OpenSRE: عامل هوشمند برای عیب‌یابی خودکار CI/CD و حوادث عملیاتی

GitHub Trending · 2026-11-25

سیستم CI به شما می‌گوید که خراب شده است، اما نمی‌گوید چرا یا چگونه آن را اصلاح کنید. OpenSRE یک عامل CLI است که اجرای ناموفق را می‌خواند، علت را ردیابی می‌کند و یک اصلاحیه برای بررسی شما ارسال می‌کند. این ابزار به صورت خود-میزبانی (Self-hosted) و با مدل‌های اختصاصی خودتان اجرا می‌شود.

🚧 آلفای عمومی: جریان‌های کاری اصلی برای اکتشافات اولیه قابل استفاده هستند، اگرچه هنوز کاملاً پایدار نیستند. این پروژه در حال توسعه فعال است و APIها و یکپارچه‌سازی‌ها ممکن است تغییر کنند.

مطمئن شوید که موارد زیر را دارید:

- یک ترمینال باز در یک پروژه کدنویسی

- یک مخزن Git (برای نمایش کامل جریان کاری توصیه می‌شود)

macOS یا Linux:

curl -fsSL https://install.opensre.com | bash -s -- -gh

Windows (PowerShell):

& ([scriptblock]::Create((irm https://install.opensre.com/install.ps1))) -gh

سپس OpenSRE را اجرا کنید:

opensre

جزئیات ویندوز: Windows.

نصب‌کننده، آخرین نسخه ساخت (build) را از شاخه main بدون نیاز به sudo دریافت می‌کند. اگر دستور opensre پیدا نشد، دستورالعمل‌های PATH چاپ شده توسط نصب‌کننده را دنبال کنید یا یک ترمینال جدید باز کنید.

برای پلتفرم‌های پشتیبانی‌شده و عیب‌یابی، به بخش Install locally مراجعه کنید.

هر ماه، هوش مصنوعی بخش بیشتری از کد را می‌نویسد. با این حال، هنوز کسی باید خرابی‌های build را اصلاح کند.

وقتی CI قرمز می‌شود، به شما می‌گوید که چیزی شکست خورده است، نه اینکه چرا یا چگونه آن را اصلاح کنید. تحت فشار مهلت‌های زمانی، تیم‌ها دکمه اجرای مجدد (re-run) را می‌زنند و به کار خود ادامه می‌دهند، بررسی‌های نامطمئن (flaky) روی هم انباشته می‌شوند، شاخه main قرمز می‌ماند و بررسی واقعی منتظر می‌ماند تا هر مهندس ارشد که وقت دارد به آن رسیدگی کند. OpenSRE یک عامل متن‌باز برای قابلیت اطمینان CI/CD است که این بررسی را برای شما انجام می‌دهد و برای اجرا روی زیرساخت خودتان با مدل‌های خودتان ساخته شده است:

- بازیابی سریع‌تر از buildهای قرمز: لحظه‌ای که یک اجرا شکست می‌خورد، آن را بررسی می‌کند، لاگ‌ها را می‌خواند، فرضیه‌ها را آزمایش می‌کند و یک اصلاحیه برای بررسی شما ارسال می‌کند.

- اصلاح علت، نه فقط اجرای مجدد: خرابی‌های ناشی از CI را از خرابی‌های ناشی از کد جدا می‌کند تا بتوانید مورد درست را اصلاح کنید.

- آگاهی از هزینه‌های CI: نرخ خرابی، ساعات کاری تلف شده توسعه‌دهندگان برای CI غیرقابل اعتماد و مدت زمانی که شاخه main قرمز می‌ماند.

- سطح دانش ارشد برای همه: هر مهندس همان عمق تحلیل را دریافت می‌کند.

پروژه SWE-bench1 نشان داد که عامل‌ها با وظایف واقع‌گرایانه و بازخورد شفاف، سریع‌تر بهبود می‌یابند. خرابی‌های خط لوله (Pipeline) کندتر، پر سر و صداتر و بازتولید آن‌ها سخت‌تر از وظایف کد محلی است، بنابراین ما OpenSRE را با استانداردهای زیر حفظ می‌کنیم:

- اجرای تست‌های end-to-end دنیای واقعی در سناریوهای مبتنی بر ابر (tests/e2e)

- حفظ نام‌گذاری معنایی کاتالوگ تست‌ها تا مرزهای e2e در مقابل واحد و محلی در مقابل ابری مشخص باقی بماند (tests/README.md)

با مرور کلی CI/CD شروع کنید: قابلیت اطمینان CI یک مخزن را تحلیل کنید، بررسی‌های ناموفق در یک PR را اصلاح کنید یا عاملی را تنظیم کنید که CI را سبز نگه دارد.

نه فقط CI/CD. همین عامل حوادث تولید (production) را در سراسر استک شما بررسی می‌کند. یکپارچه‌سازی‌هایی که استفاده می‌کنید، مانند EKS، EC2، CloudWatch، Kubernetes، Grafana (Loki, Mimir/PromQL, Tempo)، Alertmanager، Datadog، Slack و GitHub را متصل کنید. سپس حادثه را در شل تعاملی توصیف کنید یا هشدارها را به آن هدایت کنید. OpenSRE ابزارهای مناسب را انتخاب می‌کند، از لاگ‌ها و متریک‌ها گرفته تا وضعیت پاد (pod) و تاریخچه استقرار.

1 https://arxiv.org/abs/2310.06770

مشارکت‌کنندگان: برای نقشه نقطه ورود فرآیند، از main.py شروع کنید.

برای ورود به سیستم و شروع کار، opensre را اجرا کنید. اولین اجرا، مدل میزبانی‌شده را فعال می‌کند.

opensre

مشارکت‌کنندگان در وب‌اپلیکیشن می‌توانند برای احراز هویت از طریق http://localhost:3000 دستور opensre setup --dev را اجرا کنند.

شل تعاملی — بدون زیردستور، opensre حساب شما را اعتبارسنجی کرده و یک REPL را شروع می‌کند (نیاز به TTY دارد). می‌توانید خارج شوید و از سیستم خارج بمانید، اما شل فقط برای یک حساب فعال باز می‌شود. حوادث را با زبان ساده توصیف کنید، کار کردن عامل را تماشا کنید و از دستورات اسلش برای کنترل نشست (/help, /status, /cost, /sessions, /resume, /compact, /new, /exit) و یکپارچه‌سازی‌ها (/integrations list, /integrations verify) استفاده کنید. Ctrl+C یک چرخه در حال اجرا را بدون از دست دادن وضعیت نشست لغو می‌کند. برای مرجع کامل، دستورات شل تعاملی را ببینید.

CLI بدون رابط کاربری (Headless) — یک چرخه عامل را به صورت غیرتعاملی از یک ترمینال، اسکریپت یا CI job اجرا کنید:

opensre ask "why is checkout-api slow?"

برای اعلان‌های stdin، خروجی JSON و تأیید ابزارها، به بخش Headless CLI مراجعه کنید.

از طریق Python — عامل را به صورت درون‌فرآیندی از کد خودتان هدایت کنید (نیاز به دریافت سورس کد دارد):

from surfaces.embedded import start_embedded_session

session = start_embedded_session()

result = session.chat("why is checkout-api slow?")

# ``answered`` برای هر متن پاسخ، از جمله فراخوانی ناموفق مدل، درست است.

# آن شکست، accounting_status را روی "not_run" و stop_reason را روی "error" تنظیم می‌کند.

if result.action_result.accounting_status == "completed" and not result.cancelled:

print(result.primary_response_text)

برای نشست‌ها، گفتگوها و خروجی‌های سفارشی، به Python API مراجعه کنید.

برای چرخه روزانه تیم خود: OpenSRE را در سرویس‌های پایتون و اتوماسیون‌هایی که همکارانتان قبلاً استفاده می‌کنند، تعبیه کنید. با راهنمای Python API درون مخزن شروع کنید، سپس هر روز از آن استفاده کنید تا پاسخ به حوادث را تکرارپذیر کنید.

سایر دستورات مفید:

opensre integrations setup

opensre update

opensre uninstall # حذف opensre و تمام داده‌های محلی

یک درگاه مدیریت‌شده OpenSRE Cloud، یک مسیر AWS EC2 و یک گزینه کلی خود-میزبانی:

- درگاه مدیریت‌شده OpenSRE Cloud: مدیر سازمان آن را در وب‌اپلیکیشن فراهم می‌کند؛ کاربران شل که وارد سیستم شده‌اند می‌توانند بدون مدیریت اعتبارنامه‌های زیرساخت به صورت محلی، آن را بررسی، شروع یا متوقف کنند.

- درگاه (AMI + systemd): دستور make build-gateway-image و سپس make deploy-gateway را اجرا کنید — فقط درگاه تلگرام، بدون Docker؛ درگاه در یک ایمیج سرور نصب می‌شود که سرورهای جدید از آن شروع می‌شوند.

- کانتینر خود-میزبانی (Railway / ECS / Vercel): فایل Dockerfile مخزن را مستقر کنید، MODE را انتخاب کنید و LLM_PROVIDER به همراه کلید API آن را تنظیم کنید. فقط زمانی از DATABASE_URL استفاده کنید که درگاه به وضعیت مشترک مبتنی بر Postgres نیاز دارد، مانند نسخه‌های Slack Events API.

هنگامی که یک اجرای CI شکست می‌خورد، هشداری می‌رسد یا شما سوالی می‌پرسید، OpenSRE به طور خودکار:

- زمینه مربوطه را دریافت می‌کند: بررسی‌های ناموفق و لاگ‌های CI، کامیت‌ها و استقرار‌های اخیر و لاگ‌ها، متریک‌ها و تریس‌های مرتبط.

- شناسه‌های حساس را قبل از فراخوانی‌های LLM خارجی ماسک می‌کند (اختیاری).

- در سیستم‌های متصل شما استدلال می‌کند تا فرضیه‌ها را در یک چرخه فراخوانی ابزار آزمایش کند و خرابی‌های ناشی از CI را از خرابی‌های ناشی از کد جدا کند.

- با پاسخی مستند به شواهد در گفتگو پاسخ می‌دهد.

- علت را اصلاح کرده و آن را برای بررسی شما به شاخه PR ارسال می‌کند، یا مراحل بعدی را پیشنهاد می‌دهد و در صورت تمایل، اقدامات اصلاحی را اجرا می‌کند.

- خلاصه‌ای را مستقیماً در Slack، PagerDuty یا Telegram ارسال می‌کند — بدون نیاز به تغییر زمینه (context switching).

برای معماری عامل در سطح کد فعلی پس از حذف لایه‌های قدیمی گراف و فریم‌ورک زنجیره‌ای، به AGENTS.md مراجعه کنید.

OpenSRE به بیش از ۶۰ ابزار و سرویس در سراسر استک ابری مدرن متصل می‌شود، از ارائه‌دهندگان LLM و پلتفرم‌های مشاهده‌پذیری گرفته تا زیرساخت، پایگاه‌های داده و مدیریت حوادث.

OpenSRE توسط جامعه ساخته شده است. به دنبال اولین مشارکت امن هستید؟ تیکت‌های good first issue را مرور کنید یا راهنمای Good First Issues را ببینید. برای جریان کاری کامل، CONTRIBUTING.md را ببینید.
