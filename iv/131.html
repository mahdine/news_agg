توسعه‌دهندگان پایتون مستنداتی برای «خنثی‌سازی تریگرهای خطرناک در GitHub Actions» منتشر کردند

Slashdot · 2026-11-22

دو توسعه‌دهنده امنیتی در Python Software Foundation هشدار می‌دهند: «تعداد انگشت‌شماری از تریگرهای GitHub Actions به یک غریبه در اینترنت اجازه می‌دهند تا گردش‌کاری (workflow) را آغاز کند که ممکن است به اسرار (secrets) شما دسترسی داشته باشد.»

آیا تریگرهای خطرناک باعث حوادث واقعی شده‌اند؟ بله، بارها و بارها... نگهدارندگان این پروژه‌ها بی‌دقت نبوده‌اند. این تریگرها در یک فایل گردش‌کار بی‌خطر به نظر می‌رسند و نسخه ناامن تنها یک خط با نسخه امن فاصله دارد...

هنگامی که شخصی یک pull request از یک fork باز می‌کند، تریگر pull_request کد او را با یک توکن فقط‌خواندنی و بدون دسترسی به هیچ‌گونه secret اجرا می‌کند. این نسخه امن است. pull_request_target در فایل گردش‌کار تقریباً مشابه به نظر می‌رسد اما رفتار بسیار متفاوتی دارد. این تریگر با یک توکن خواندن/نوشتن و دسترسی به اسرار مخزن و سازمان شما اجرا می‌شود. GitHub آن را برای کارهای ساده‌ای مانند برچسب‌گذاری pull requestها از forkها ساخته است، جایی که گردش‌کار هرگز با کد مشارکت‌کننده تماسی ندارد. مشکل زمانی شروع می‌شود که یک گردش‌کار، pull request را checkout کرده و به هر حال آن را اجرا می‌کند... هر کسی که یک حساب GitHub داشته باشد می‌تواند آن pull request را باز کند. کد آن‌ها اکنون با اعتبارنامه‌های شما اجرا می‌شود. به این وضعیت "pwn request" گفته می‌شود و مستندات GitHub آن را عامل اصلی چندین مورد نفوذ به زنجیره تأمین (supply-chain) توصیف می‌کنند.

تریگر issue_comment نیز همین خطر را به همراه دارد. این تریگر زمانی فعال می‌شود که هر کسی روی یک issue یا pull request نظری ثبت کند و گردش‌کار با توکن و اسرار مخزن اجرا شود... گاهی اوقات گردش‌کار، متن نظر را در یک دستور shell قالب‌بندی‌شده قرار می‌دهد و مشخص می‌شود که آن نظر، دستورات متفاوتی را به shell گردش‌کار تزریق می‌کند.

Seth Larson، توسعه‌دهنده امنیتی رسمی پایتون، به همراه Mike Fiedler، مهندس ایمنی/امنیت PyPI، برای حذف این تریگرهای خطرناک و همچنین اعمال سیاست‌ها در سازمان‌های GitHub تحت مدیریت Python Software Foundation (شامل psf، python و pypi) همکاری کردند. آن‌ها همچنین مستندات فنی در مورد نحوه پیاده‌سازی این سیاست‌ها برای پروژه‌ها و سازمان‌های خودتان تهیه کرده‌اند.

«در طرح GitHub Team یا Enterprise، می‌توانید آن‌ها را برای هر مخزن در سازمان خود با یک سیاست واحد غیرفعال کنید. در طرح Free، می‌توانید این کار را برای هر مخزن به صورت جداگانه انجام دهید. سیاست را تنظیم کنید، بررسی کنید که چه چیزی را مسدود می‌کند و سپس آن را اعمال نمایید.»
