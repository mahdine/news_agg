# Live worker — instant full translation + continuous feedback

The always-on half of the runtime: a Docker container in WSL owning user-facing interaction and feedback collection. The hourly Actions run stays the pipeline (fetch/rank/translate/post/state commit).

## Why this shape (hard-to-reverse decisions)
- **Single update consumer.** Two long-poll consumers on one bot split updates randomly — each update is delivered to exactly ONE consumer. The worker consumes ALL update types; the Actions run must NOT call getUpdates (`drain_feedback` was removed from main.py). Missing reactions/votes ⇒ suspect a second poller, not Telegram.
- **File-based handoff, not shared state.** The worker never writes state.json. It pushes only `iv/*.html` and `live/feedback.json` (fetch → `reset --hard origin/main` → re-copy file → commit → push, ×3 retry). Different files = no commit conflict with the hourly state commit.
- **Trigger, two tiers.** PRIMARY: when the pipeline pre-deployed the page before posting (`main._pretranslate`), the `t.me/iv?url=…&rhash=…` link goes IN THE POST TEXT (`build_message(translate_url=…)`, line `📄 <a href="…">ترجمه‌ی کامل</a>` after the body) and NO «ترجمه کامل» button is added — the worker is not involved. **A `t.me/iv` link inside a URL BUTTON opens in the EXTERNAL browser (redirects to the domain); only links in message text open Instant View in-app (observed 2026-11-22, post 108 — never put the IV link back in a button).** Legacy posts 108/111–115 (pre-fix) instead point the «ترجمه کامل» button DIRECTLY at the page URL (one tap, in-app webview) — the Bot API cannot read an old post's text (no getMessage endpoint) and the Persian summary is not persisted, so their body is unrecoverable. FALLBACK (posts with no fetchable article body — Bluesky, paywall, fetch failure): the button is `t.me/share/url?url=<article>&text=<TRANSLATE_SHARE_PREFIX + bot username>` — the share dialog always delivers a REAL message (prefix + article URL) to the bot PM for every user; the worker matches the prefix, regexes out the first URL, then resolves it to the posted post's pid via `state.posts` (URL match) so the page key stays `iv/<pid>.html` (reusing the pipeline's page); unknown URLs keep the slug key. A forward (`forward_from_message_id` + `forward_from_chat.id` verifies our channel) and `/t <message_id|url>` remain fallbacks. Deep-link `?start` is a DEAD END as a trigger: the payload fires only on FIRST start — a returning user's click generates no event at all. Every DONE message ends with NEXT_STEPS so the chat's last message is always fresh guidance.
- **Instant UX is a requirement.** Any user-tap feature must respond within a minute; the hourly cadence applies only to the pipeline.

## Translation flow (src/live.py → translate_full → ivpage → Pages)
1. Forward, /t, or the post's «ترجمه کامل» button (share-dialog message: TRANSLATE_SHARE_PREFIX + article URL, regexed out of the text) → job thread with its OWN httpx.Client (httpx is not thread-safe; the poll loop must not block on the job either).
2. Resolve: a numeric key is AMBIGUOUS — pid (direct) or channel message_id (forward//t). Check `key in state.posts` FIRST, then `State.find_pid_by_message`; pids are small (next_post_id), channel message_ids are large — don't rely on magnitude, the posts check makes it unambiguous. A /t URL skips state. A share-dialog URL of an ALREADY-POSTED article is remapped to that post's pid (same URL in `state.posts`) before any work.
3. **HEAD short-circuit (`_page_ready`)**: if the page URL is already 200 (pipeline pre-translated before posting, or an earlier request), reply DONE immediately — no quota burn.
4. `article.fetch` (trafilatura, ≤8000 chars) → None means paywall/JS challenge → honest failure message + original link.
5. `translate.translate_full` — full-translation prompt, same free-tier model chain as summarize (20 RPD per model; 429 = exhausted). Cache in /data/translated.json keyed by pid+url so a re-forward doesn't burn quota.
6. `ivpage.build_page` — minimal RTL HTML (`dir="rtl"`, `<article>`, `<h1>`, `<p>` per paragraph, escaped; original link in footer) so Telegram's GENERIC Instant View parser works without a template.
7. Push `iv/<pid>.html` to main → `iv-deploy.yml` (on: push, paths iv/**) deploys the Pages site.
8. Worker HEAD-polls the page URL until 200 (≤4 min) and DMs the link. URL is deterministic: `https://mahdine.github.io/news_agg/iv/<pid>.html`.

## Pages facts
- Repo is PUBLIC; Pages project page `mahdine.github.io/news_agg` (already live for the scorecard).
- BOTH workflows deploy the same site structure (index.html = scorecard + iv/*.html) — change staging in both or the hourly deploy drops the article pages.
- **iv-deploy race (fixed 2026-11-21):** deploy-pages@v4 queries the artifact index ~0.3–0.6s after upload finalization; sometimes the artifact isn't indexed yet → "No artifacts named 'github-pages' were found" even though the upload succeeded (artifact is visible via API seconds later). `iv-deploy.yml` has a `sleep 20` between upload-pages-artifact and deploy-pages — don't remove it. The hourly publish.yml runs without the sleep and has not hit it, but shares the same latent race.
- Instant View only renders for domains with an IV template (Telegram-maintained + some community). Most of this feed's domains (news.ycombinator.com, github.com, 404media.co, bsky.app, cnews.ru/vc.ru/mail.ru) have none — IV cannot be the reading path for ORIGINAL articles; it is a delivery format only for pages WE host (own domain ⇒ generic parser or own template).
- If in-app rendering is bad: author a template at instantview.telegram.org for mahdine.github.io.

## Feedback handoff
- Worker records reactions (message_reaction + message_reaction_count), /start votes, poll answers/closings, callback votes in an in-memory State; every ≥60s when dirty it pushes `live/feedback.json` ({last_update_id, posts: {pid: {votes, reaction_counts, poll_counts}}}).
- Hourly run: `State.apply_live_feedback(ROOT/"live"/"feedback.json")` in main.py BEFORE scoring + scorecard (feedback_reweight consumes the votes). Overwrite semantics are safe: the worker is the sole writer of those fields and builds from the latest state.json (on refresh it adopts only NEW pids, keeps its own feedback records).
- Offset lives in /data/offset in the container, seeded from state.last_update_id on first start. Telegram holds undelivered updates ~24h, so a stopped worker catches up on boot (cutover double-processing is idempotent; worst case a duplicate /start confirmation).

## Pitfalls (learned the hard way)
- **getUpdates offset = last_id + 1 (Telegram semantics).** The worker's /data/offset stores the NEXT offset; state.json `last_update_id` keeps the legacy "last processed id" semantics (snapshot writes `offset - 1`, startup seed reads `last_update_id + 1`). Dropping the +1 makes Telegram re-deliver the LAST update forever → the worker reprocesses it on every poll → the same reply sent in a tight loop (2026-11-21 spam incident: one forwarded post = endless identical messages until the container was killed). Reactions hid it because re-recording is idempotent and silent; any message-type update (forward, /start, /t) makes it visible.
- **Logging is invisible in spam diagnosis:** the forward/rejection paths log nothing on success, and SIGKILL loses unflushed stdout — diagnose from the offset file + git log + API, not the logs.

## Deploy (WSL; separate from tg-media-bot — standing user rule)
- Docker daemon access from Windows: **`wsl -u root -e sh -c "docker ..."`** — the default WSL user (mahdi) is NOT in the docker group (socket root:docker); `wsl -e`/`wsl -u mahdi` gets "permission denied". WSL output through the Windows relay is UTF-16 — redirect to a file (`> /c/…/out.bin`) and `cat` it for clean text.
- Home: `~/news-live` (WSL home) — own clone, own .env, container `newsagg-live`, data in ./data. Never mix code/env/containers with tg-media-bot.
- .env: production TELEGRAM_BOT_TOKEN + TELEGRAM_CHANNEL=@ai_news_agg (the PRODUCTION channel — @persiantechtwiter retired 2026-11-21; a worker pointing at the wrong channel rejects every legitimate forward with NOT_OUR_CHANNEL) + GEMINI_API_KEY (from GH Secrets — the local .env key is stale/invalid) + GITHUB_TOKEN = fine-grained PAT on news_agg (Contents: read+write), used only for the worker's pushes. NOTE: the PAT has NO Actions permission (workflow rerun API → 403); trigger workflow re-runs by pushing a change instead.
- First time: `bash docker/bootstrap.sh` (clones repo, sets git identity) then `docker compose -f docker/docker-compose.yml up -d --build live`. Later code changes: `git pull` in the repo volume only — the Dockerfile has NO COPY of source (WORKDIR /repo), so the container runs the volume's code; no rebuild needed. A push alone does NOT change the running worker: `refresh_state` resets /repo to origin/main within 60s, but the process keeps the OLD code in memory — after the volume has synced, `docker restart newsagg-live` (or compose restart) to load the new code.
- **`docker compose restart` does NOT reload .env** (env_file loads at container creation) — after editing .env use `docker compose up -d --force-recreate live`.
- Privoxy on the WSL host bridges the container to the user's SOCKS5 relay: `listen-address 0.0.0.0:8118` (NOT 127.0.0.1 — the container reaches it via host.docker.internal = 172.17.0.1) and `forward-socks5 / proxy.shenakhtic.ir:8124 .` — the 3-argument syntax is the only form privoxy accepts (2- or 4-arg lines are silently ignored → traffic goes DIRECT and 403s from Iran). Enabled via systemd. `GEMINI_HTTP_PROXY=http://host.docker.internal:8118` routes ONLY Gemini through it.
- Docker Hub pulls also 403 from Iran: daemon proxy via systemd drop-in `/etc/systemd/system/docker.service.d/proxy.conf` (HTTP_PROXY/HTTPS_PROXY=http://127.0.0.1:8118) — affects `docker pull`/build only, not container runtime traffic.
- **`git diff --cached --quiet` exit 1 means "changes present", NOT an error** — wrapping it in a "nonzero = failure" git helper turns every fresh commit into a spurious retry (caught by the container E2E 2026-11-21; `main._commit_iv` handles rc 0/1/≥2 explicitly).
- **A push made from inside a GitHub Actions workflow does NOT trigger other `on: push` workflows** (loop prevention; verified 2026-11-22: overnight iv pages pushed from the publish run never woke `iv-deploy.yml` → every post's «ترجمه کامل» fell back to the share dialog even though the page was committed). External pushes (worker container) trigger normally. Fix: `main._pretranslate` calls `_dispatch_iv_deploy()` — `POST /repos/{o}/{r}/actions/workflows/iv-deploy.yml/dispatches` (needs `actions: write` in publish.yml; `workflow_dispatch:` trigger in iv-deploy.yml). **Root cause of the silent failure (probe 2026-11-22): GitHub no longer auto-injects the `GITHUB_TOKEN` env var into steps (len=0) — only the `github.token` expression works (~377-char token; same long-token that breaks git 2.47's URL parser → GIT_ASKPASS note). publish.yml passes `GITHUB_TOKEN: ${{ github.token }}` in the bot step's env. The end-of-run Pages deploy still lands the page a few minutes later either way — the dispatch only makes it live BEFORE the post.**
- **git push from the container uses GIT_ASKPASS, not token-in-URL** (`src/live.py::_git_push`): git 2.47's URL parser rejects long tokens (≥~90 chars) embedded in `https://user:token@…` with "URL rejected: Port number was not a decimal number" (reproduced with a dummy token of the same length — it's a parser bug, not the token). The ASKPASS temp script (chmod 700, deleted after) keeps the token out of the URL.
- **Pre-translate E2E lives in the container, not Actions**: `docker cp` a scratch script in, `docker exec newsagg-live python` it, driving `main._pretranslate` with real env (proxy + models from /repo/config.yaml) — but set up `GIT_ASKPASS` (token in URL breaks git 2.47's parser) since Actions embeds the token in the remote while the container's /repo does not.
- The pipeline's pre-translate burns ONE `translate_full` per posted article (quota); posts without fetchable body (Bluesky etc.) skip it and get the share-fallback button — the run is NEVER delayed by a failed pre-translate (all failures → fallback).
- Dockerfile carries `git config --system --add safe.directory /repo` (container git runs as root over a user-owned volume).
- WSL repo sync: the outer `~/news-live` clone AND the inner `~/news-live/repo` (the /repo volume) both need `git pull`/`fetch + reset --hard origin/main` — the worker pushes from the inner repo. Uncommitted local edits in the outer clone block `git pull` (stash → pull → the upstream often already contains the fix from a parallel session).

## Instant View template (instantview.telegram.org)
- A domain template for `mahdine.github.io` EXISTS (created 2026-11-21, v2.1). The editor auto-created an empty v1.0 shell on first visit — that's why pages showed "No Instant View available" until rules were written.
- Rules (see SKILL.md "Instant View" section for the full list): `?path: /news_agg/iv/.*.html` · `title: //h1` · `body: //article` · `@remove: //article/h1` · `cover: //img[@class="hero"]` · image_url/description/site_name · `channel: "@ai_news_agg"` (join button).
- **The worker sends `t.me/iv?url=…&rhash=…`** (`iv_link()` in live.py; `IV_RHASH` constant, env-overridable). rhash pins the template REVISION: every template edit in the editor mints a new rhash — read it from the editor's "View in Telegram" link (`t.me/share/url?url=…rhash=…`, double-encoded) and update `IV_RHASH` in the same change. rhash links need NO Telegram approval (own-audience publishing).
- Editor mechanics: rules live in a CodeMirror bound to `window.App.editor`; SAVE = call `saveRules()` (Ctrl+S key dispatch is focus-flaky — don't rely on it; the editor also auto-saves 5s after any change). The hidden CM (172 lines) is Telegram's global extra-rules reference, not a second editor. `?path:` regex = single leading slash, NO closing slash (a trailing `/` becomes part of the regex and silently matches nothing → "No Instant View available").
- Login: phone → in-app Telegram confirm tap; temp_session expires ~5 min; session is PER-TAB (sessionStorage) — opening a new tab loses it. The 3-column editor renders only at wide viewports (set `Emulation.setDeviceMetricsOverride` ≥1800px). "Reload" in the header re-fetches the SOURCE page; the status line under PREVIEW ("Instant View successfully generated" / "No Instant View available") reflects the last server-side evaluation.
